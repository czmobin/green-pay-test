# گرین‌پی — سامانهٔ جلسات سازمانی

سامانهٔ داخلی مدیریت جلسات گرین‌پی: تقویم شمسی، ساخت و ویرایش جلسه، دستور جلسه،
صورت‌جلسه به تفکیک هر شرکت‌کننده، یادآور پیامکی، تشخیص تداخل زمانی و اتاق،
اشتراک تقویم بین همکاران، و همگام‌سازی دوطرفه با Outlook سازمانی.

نسخهٔ در حال اجرا: <https://calendar.greenpay360.ir>

---

## معماری در یک نگاه

دو سرویس مستقل که در production پشت یک دامنه جمع می‌شوند:

```
                    nginx  (۸۰ و ۴۴۳)
                      │
      ┌───────────────┼────────────────────┐
      │               │                    │
  /api  /admin    /static  /media      بقیهٔ مسیرها
      │               │                    │
   gunicorn        فایل‌های                Next.js
 Django 5.0        Django              (127.0.0.1:3000)
(127.0.0.1:8001)
      │
 PostgreSQL 16
(127.0.0.1:5432)
```

فرانت‌اند هیچ منطق دامنه‌ای ندارد و همهٔ دادهٔ خود را از API می‌گیرد. نقطهٔ شروعش
`GET /api/bootstrap/` است که در یک درخواست همهٔ چیزی را که اپ لازم دارد برمی‌گرداند
(جلسات، افراد، محل‌ها، صورت‌جلسه‌ها، یادآورها، اشتراک‌های تقویم). بقیهٔ endpointها
فقط برای نوشتن‌اند.

احراز هویت با **JWT** است و نشست (session) در کار نیست. ورود با شمارهٔ موبایل انجام
می‌شود: کد یک‌بارمصرف پیامک می‌شود، یا اگر کاربر قبلاً رمز تعیین کرده، با رمز.
پنل ادمین جنگو مسیر جداگانهٔ خودش را دارد و با نشست کار می‌کند.

دو کار زمان‌بندی‌شده هم هست که با تایمر systemd هر دقیقه اجرا می‌شوند: ارسال یادآور
پیامکی، و همگام‌سازی Outlook. خبری از Celery و صف و بروکر نیست — برای این حجم کار
لازم نبود.

|---|---|---|

بیرون از این فهرست وابستگی دیگری نیست. برای تماس با سرویس‌های بیرونی (پیامک و

`httpx` به پروژه اضافه نشوند.

## راه‌اندازی محلی

### پیش‌نیاز

Python 3.10 یا بالاتر، Node 18.17 یا بالاتر. روی سرور Python 3.12 و Node 20 نصب است
و پروژه روی 3.10 هم تست شده.

### ۱) بک‌اند

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate          # ویندوز: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env               # مقادیر پیش‌فرضِ توسعه کافی‌اند
python manage.py migrate
python manage.py init_data         # انواع سازمان و دسته‌های جلسه
python manage.py runserver 8000
```

`init_data` فقط دادهٔ پایه می‌سازد (انواع سازمان، دسته‌های جلسه) و کاربر و جلسهٔ
نمونه نمی‌سازد. دیتابیس تازه خالی است.

تنظیمات از دو جا خوانده می‌شوند: اول `/etc/greenpay.env` (که فقط روی سرور هست)، بعد
`backend/.env`. اولی اولویت دارد، پس یک `.env` جامانده روی سرور نمی‌تواند مقادیر
production را عوض کند.

### ۲) فرانت‌اند

```bash
cd frontend
npm install
NEXT_PUBLIC_API_URL=http://127.0.0.1:8000/api npm run dev
```

حالا اپ روی <http://localhost:3000> بالاست.

> `NEXT_PUBLIC_API_URL` **موقع build** داخل باندل نوشته می‌شود، نه موقع اجرا. اگر با
> `npm run build && npm start` کار می‌کنید، باید همین متغیر را موقع `build` بدهید؛
> دادنش موقع `start` هیچ اثری ندارد. در production اصلاً لازم نیست، چون فرانت و بک
> هم‌دامنه‌اند و مقدار پیش‌فرض `/api` جواب می‌دهد.

### ۳) اولین ورود

اینجا یک نکته هست که اگر ندانید گیر می‌کنید: **ورود به اپ همیشه با شمارهٔ موبایل
است**، و کاربری که با `createsuperuser` می‌سازید شماره ندارد، پس فقط به `/admin/`
راه دارد نه به خود اپ.

مسیر درست:

1. در صفحهٔ ورود اپ شمارهٔ موبایل خودتان را بزنید. چون `KAVENEGAR_API_KEY` خالی است
   پیامکی فرستاده نمی‌شود و کد در پاسخِ `request-otp` زیر کلید **`devCode`**
   برمی‌گردد — در تب Network مرورگر می‌بینیدش. (این رفتار را
   `OTP_ECHO_WHEN_SMS_OFF=1` کنترل می‌کند و روی production که کلید تنظیم است بی‌اثر
   می‌ماند.)
2. با این کد وارد شوید. کاربر تازه با نقش «کاربر عادی» ساخته می‌شود.
3. برای اینکه ادمین شوید: `python manage.py createsuperuser` بزنید، با آن به
   `http://localhost:8000/admin/` بروید، کاربر خودتان را باز کنید و `role` را روی
   `admin` بگذارید.

راه کوتاه‌تر: به همان کاربر superuser در ادمین یک `phone` بدهید و بعد با همان شماره
وارد اپ شوید — نقش `admin` را هم خودکار دارد، چون `is_superuser` در سامانه معادل
ادمین حساب می‌شود.

### تست‌ها

```bash
cd backend
python manage.py test meetings
```

۵۱ تست، حدود ۸۰ ثانیه. بیشترشان روی مجوزها و همگام‌سازی Outlook‌اند — یعنی جاهایی
که باگ بی‌صدا خراب می‌کند. تست Outlook با یک کلاینت جعلی کار می‌کند و به tenant
واقعی نیاز ندارد.

## چند تصمیم که بهتر است بدانید

**production روی PostgreSQL است، توسعهٔ محلی روی SQLite.** انتخاب موتور با وجود یا
نبودِ `DB_NAME` در محیط انجام می‌شود — نه با یک پرچم جدا. دلیلش این است که
تنظیم‌کردن نیمی از مشخصات اتصال و جا انداختن پرچم، خطایی است که فقط موقع اولین
نوشتن خودش را نشان می‌دهد؛ این‌طور یا همهٔ مشخصات هست یا هیچ‌کدام.

برای توسعهٔ محلی لازم نیست PostgreSQL نصب کنید. اگر می‌خواهید محیط محلی دقیقاً
شبیه production باشد، یک کانتینر کافی است:

```bash
docker run -d --name gp-pg -e POSTGRES_DB=greenpay -e POSTGRES_USER=greenpay \
  -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:16
# بعد در backend/.env مقدار DB_NAME=greenpay و DB_PASSWORD=dev را بگذارید
```

سامانه تا شهریور ۱۴۰۵ روی SQLite بود و بعد به PostgreSQL منتقل شد. اگر به کامیت‌های
قدیمی برگشتید و جایی «WAL» یا «database is locked» دیدید، مربوط به همان دوره است.

**همگام‌سازی Outlook پیش‌فرض خاموش است** و تا وقتی `OUTLOOK_ENABLED=1` نشود حتی یک
درخواست هم به مایکروسافت نمی‌رود. مراحل روشن‌کردنش در `DEPLOY.md` است.

**هویت کاربر شمارهٔ موبایل است، نه ایمیل.** فیلد `email` روی مدل `User` هست ولی تا
پیش از Outlook هیچ‌جا استفاده نمی‌شد و برای هیچ کاربری پر نیست. همگام‌سازی Outlook
به این ایمیل‌ها نیاز دارد و راه پر کردنشان در `DEPLOY.md` توضیح داده شده.

**همهٔ متن‌های رابط فارسی و راست‌به‌چپ‌اند** و تاریخ‌ها شمسی. تبدیل تاریخ دو
پیاده‌سازی دارد — یکی در پایتون (`backend/meetings/jalali.py`) برای متن پیامک و
گزارش، یکی در تایپ‌اسکریپت (`frontend/lib/jalali.ts`) برای رابط. عمداً کتابخانهٔ
بیرونی برایش اضافه نشده.
